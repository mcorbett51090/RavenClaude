# 05 — Reviewing and updating the checks

Checked 2026-11-16. A check list rots. Jobs get renamed, a required name points at a workflow that no longer runs, a flake gets a retry, and a test starts failing when the workflow changes by a comment. The review is a scheduled pass over an inventory, with an owner for each row. The checklist is [runbook.md](runbook.md).

## Inventory

One row per required context, and one row per job that can skip:

| Column | Where it comes from |
|---|---|
| Context name | Ruleset `required_status_checks[].context`. Exact string. |
| Source app | `integration_id`, or "any source" |
| Workflow and job id | The job id, not a `name:` override |
| Trigger events | Must include an evaluated event, and `merge_group` if a queue is on |
| Path filter | Trigger-level filters on a required workflow are a defect |
| Owner | A person or a CODEOWNERS path |
| Last red that caught a real break | Date, SHA, one line |
| Duration p50 / p95 | Actions run timing |
| Flake rate | Re-runs of the same SHA that then passed, over the last 30 days |

Organization rulesets do not index check names. Copy the string from a recent run. A typo stays Pending.

## What to measure

Duration tells you what to shard or cache. It does not tell you whether the check earns its place.

Failure-catch value is the question: in the last quarter, did this check fail while the others passed, on a change that was wrong? A check that is red only when the suite is also red is a duplicate. A check that is never red is either very strong or no longer connected to the code. The deletion row includes the URL of a run from that quarter in which the job executed, so the review can see the assertion still ran. A check that is always red is not a gate. Fix it or take it off the required list. An always-red required check teaches people to bypass.

Flake rate above a small threshold gets a quarantine row: owner, issue, date it leaves the required job. Retries of the assertion itself count as flakes, not as passes.

## Cadence

| When | What |
|---|---|
| Every change to a workflow or a ruleset | The contract test, `actionlint`, `zizmor`. Read the ruleset back after the API write. |
| Monthly | Duration and flake table. Cancel-rate on pull requests (are superseded runs still finishing?). |
| Quarterly | The full runbook. Remove or fix rows with no failure-catch and no owner. Re-pin or relock actions. |
| Before a suite becomes a release blocker | Confirm it is a required context from the expected app, on an evaluated event, and that a skip of that job fails the aggregate. |

Deprecate by deleting the required context in the same change that deletes the job. Leaving the context behind hangs every pull request.

## Pinning and lint

GitHub's secure-use page, retrieved 2026-11-16, says the strongest lock on action code is a workflow dependency lockfile, `.github/workflows/actions.lock`, generated by `gh actions-lock`. Public preview, changelog 2026-10-14, for Enterprise Cloud, Team, and Free. The lockfile records the commit and the source repository's numeric id, including transitive actions. A moved tag fails the run. Dependabot regenerates the lock entry in the same pull request as the version bump. Reusable-workflow calls are not locked by the current extension; pin those `uses:` to a full SHA yourself. Confirm the plan lists this preview before adopting it on a private user repository. Pro was not in the changelog's plan list.

Where the lockfile is not available, pin `uses:` to a full commit SHA and put the version tag in a trailing comment. A floating tag can be moved. Dependabot's `github-actions` ecosystem opens the bump pull requests so the pin does not rot. Dependabot does not alert on SHA-pinned actions for vulnerabilities. The version-update pull request is the review.

`actionlint` checks workflow syntax. `zizmor` checks unpinned `uses`, dangerous permissions, and script injection. Run both on the workflow directory in CI. The job that runs them has to follow the aggregate-gate rules if you require it: no trigger-level path filter, or a docs-only pull request hangs.

Immutable-release settings on the action repositories you own stop you from moving your own tags. They do nothing for third-party actions. The lockfile or the SHA pin does.

## The byte-pin anti-pattern

A test that asserts a live workflow file is byte-equal to a proposed copy fails on every comment, every timeout tweak, and every genuine fix. It also forces two edits for one change, and the edit that lands in only one copy is the one that runs. That is how a gate and its test drift in opposite directions.

Pin the contract instead:

- the job id that the ruleset names
- the absence of a `name:` key on that job
- the permissions ceiling
- the first step is the runner guard, before checkout
- the concurrency group, and that cancel is limited to pull requests
- the pull-request trigger has no `paths:`
- the aggregate job's `if:` includes `always()`, and its script fails on `failure` and `cancelled`

Keep byte equality for a script that is copied into many jobs and where a one-character drift is the bug, such as a runner-name guard inlined because the job must not checkout first. One canonical file, many copies, the test compares copies to the canonical file. It does not compare two full workflows.

A test that shells out to the gate script with a fake `needs` JSON is the right pin. It locks the decision, not the YAML bytes around it.
