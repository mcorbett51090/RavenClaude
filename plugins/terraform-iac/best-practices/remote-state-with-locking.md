# Remote state with locking is non-negotiable

Local state on a laptop is a single point of failure and a guaranteed conflict the moment a second person or a pipeline runs `apply`. Use a remote backend (S3 with native `use_lockfile = true` locking, GCS, azurerm, or Terraform/Tofu Cloud) that gives you state locking, versioning, and access control from day one. **On S3, prefer native locking over DynamoDB** — Terraform 1.11 deprecated the `dynamodb_table` locking arguments in favor of the GA S3-native lock (`[re-verified 2026-09-23]`); keep DynamoDB configured only while migrating existing state, then drop it. Locking serializes concurrent applies so two runs can't corrupt the state or race the same resource; versioning lets you roll back a botched state mutation. Never disable the lock to 'unblock' a run — a stuck lock means investigate, not `force-unlock` reflexively. State is the source of truth for what exists; treat it with the same care as the infrastructure it describes.
