# VERIFY ledger — claims with weak, indirect, or absent primary evidence

Compiled from the 2026-10-12 Wallet capability KB. Every line below is either (a)
unverified from a primary source, (b) an argument from absence of documentation, or
(c) a documented value whose underlying number Apple/Google do not publish.
**Treat each as a hypothesis, not a fact.** Re-check before any of these drives a
build decision or a customer promise.

Severity: **P1** = would change a RavenPass architecture or a customer promise · **P2**
= would change an implementation detail · **P3** = an undocumented number recorded as
"unknown". The **8 P1 items (#1–#8)** also carry an inline `⚠️ P1 unverified (#n)` note
at their claim site in the relevant reference — do not treat the claim as settled there.

> **How to read a claim that cites one of these.** Anywhere a reference says a thing
> "see verify.md #N" or carries a `P1 unverified (#N)` note, the surrounding text is the
> **working belief**, not a contract. If you are about to promise it to a customer or
> wire an irreversible build decision to it, run the "How to verify" step first.

## P1 — architecture / promise level

- Unverified: **#1 (P1)** — the single-pass MIME type is `application/vnd.apple.pkpass` and serving it over HTTPS triggers Safari's inline Add-to-Wallet sheet. The current Wallet Passes pages only document the **bundle** type `application/vnd.apple.pkpasses`; the single-pass type was on no page fetched. Long-standing in practice. How to verify: serve a real `.pkpass` with that `Content-Type` from a test HTTPS endpoint and open in Safari on a current iPhone; cross-check the archived PassKit Package Format Reference.
- Partly resolved 2026-10-14: **#2 (P1)** — a `.pkpass` download works in non-Safari iOS browsers and in Android browsers. **Now evidenced:** Chrome for iOS presents the Add sheet itself (DOC, Chromium source: `PassKitTabHelper` handles `application/vnd.apple.pkpass` → `PKAddPassesViewController`); Firefox for iOS fixed it in v5.0 (Bugzilla 1250209); on Android, **Google Wallet imports a downloaded pass** ("Select Google Wallet", Continue — DOC support.google.com/wallet/answer/12060038) but warns a converted pass "may not get updates." **Still open:** Edge iOS, and in-app browsers — Apple (DOC, archived *Distributing Passes*): only Safari and Safari View Controller import a pass directly; a web view must intercept and add it itself; MEAS (developer forum 844595, 2026-09): blocked inside Instagram and Messenger. How to verify the rest: test Edge iOS and the LinkedIn / TikTok in-app browsers on a current iPhone.
- Unverified: **#3 (P1)** — `posterGeneric` is a real, supported top-level `pass.json` key. Documented in the **guide** ("Creating a Poster Generic Pass") with a full code sample, but **absent from the `Pass` reference property table** as of 2026-10-12 (zero occurrences of "posterGeneric" in the Pass DocC JSON). Could be doc-sync lag, a beta-gated key, or a rename. How to verify: build a pass with `posterGeneric` + a `generic` fallback and install on an iOS 27 device; re-check the `Pass` reference in ~30 days.
- Unverified: **#4 (P1)** — Google Wallet passes are usable on iOS. Not stated on any page fetched. Evidence added 2026-10-14: saving "can only be initiated in the context of a logged-in Google identity" (DOC, generic/web) and iOS recipients of a shared Google pass got a **web UI** (MEAS, 9to5Google 2023) — so treat iPhones as Apple-only and hide the Google button there. `AppLinkData.iosAppLinkInfo` is deprecated ("Links to open iOS apps are not supported"), which hints Android-first but is not a statement about pass availability on iOS. How to verify: open a `https://pay.google.com/gp/v/save/<jwt>` link on an iPhone and record the result; find the primary supported-platforms page.
- Unverified: **#5 (P1)** — no public NameDrop API exists for third-party apps (so RavenPass cannot originate, intercept, populate, or receive a NameDrop exchange). Argument from absence: a developer.apple.com search surfaced only forum threads. How to verify: grep the PassKit / Contacts / `UIActivityItemsConfiguration` references for any NameDrop surface; check WWDC 2023–2026 session indexes for "NameDrop."
- Unverified: **#6 (P1)** — Apple Wallet NFC passes are invisible to ordinary NDEF readers (iPhone background tag reading, Android `ACTION_NDEF_DISCOVERED`). Inferred from two facts (pass `nfc` = VAS protocol; reading VAS needs `NFCVASReaderSession` + a `GET VAS DATA` command). Apple never says "a pass does not emit NDEF." How to verify: hold an iPhone with an NFC-enabled pass against an Android NDEF-reader app and against an iPhone doing background tag reading; record that nothing is detected.
- Unverified: **#7 (P1)** — Apple's NFC pass (VAS) certificate request has no published SLA. Verified only that `/contact/passkit/` is sign-in gated (302 → idmsa.apple.com), so the form wording and any SLA are not publicly inspectable. The cited "1–2 weeks" is forum anecdote only. How to verify: sign in with the RavenPass Apple Developer account, read the form, record what it asks and any stated timeline.
- Unverified: **#8 (P1)** — Google `appLinkData` (the front-of-pass button) requires allowlisting. Stated once, in the FAQ ("Applinking requires allowlisting which can be requested here"), with no criteria, eligibility, form content, or timeline; the linked form was not fetched. **This gates whether RavenPass can put a tappable "Share your details" button on the front of a Google pass.** How to verify: open the FAQ's "requested here" link while signed into the Google Pay & Wallet Console; capture the form fields and any stated review time.

## P2 — implementation detail

- Unverified: **#9 (P2)** — `backFields` values containing a URL, phone number, or email are auto-linked (data detectors) by Wallet. Universally observed in practice; **not stated** on any page fetched. How to verify: build a test pass with a bare `https://`, `tel:`, and `mailto:` in `backFields` and inspect on current iOS.
- **Resolved 2026-10-14: #10 (P2)** — Wallet's Share sheet channels. DOC, [Wallet & Privacy](https://www.apple.com/legal/privacy/data/en/wallet/): "Wallet allows you to share passes by AirDrop, iMessage, Mail, or with third-party mail, messaging, or other communication apps." (Kept here so the number is never reused.)
- Unverified: **#11 (P2)** — the exact `pass.json` schema for declaring iOS 27 Featured Actions. Apple documents the action **identifiers** (`call`, `place`, `shop`, `bookAppointment`, `viewOffersRewards`, …) and says each has "an icon, string, and action," but no JSON key, nesting, or URL field is documented. How to verify: look for a `featuredActions`/`passActions` key in the DocC JSON for `Pass`/`SemanticTags`/Pass Designer; else inspect a shipped iOS 27 poster pass or file a DTS question.
- Unverified: **#12 (P2)** — `com.apple.developer.nfc.readersession.formats` still accepts the value `NDEF`. The current reference lists only `TAG`. Historically both `NDEF` and `TAG` were valid. How to verify: check the Xcode capability UI and a current entitlements file; cross-check `NFCNDEFReaderSession`'s own entitlement requirement.
- Unverified: **#13 (P2)** — the required/recommended NFC tag type for a plain URL business-card tag. Apple documents Type 5 only for NFC-integrated App Clip Codes; Core NFC reads types 1–5. Nothing says which type to buy for a plain URL tag. How to verify: test NTAG213/215/216 (Type 2) tags against current iPhones and Android 17 devices; confirm capacity for the chosen URL.
- Unverified: **#14 (P2)** — Android QR scanning via Camera / Google Lens works as assumed. No Google primary-source page was retrieved for this. How to verify: find the support.google.com page for "Scan a QR code with your Android phone" and quote it.
- Unverified: **#15 (P2)** — iOS behavior when Safari *downloads* a `.vcf` from a web page. Apple documents only "tap a `.vcf` attachment in an email or message"; the browser-download path is undocumented and has changed across iOS versions. How to verify: test `Content-Type: text/vcard` download, `Content-Disposition: inline` vs `attachment`, and a `data:`/blob URL on current iOS.
- Unverified: **#16 (P2)** — Android Beam / phone-to-phone NDEF push is gone. Argument from absence: the current Android NFC guide never mentions Beam. How to verify: find an Android release-notes/behavior-changes page that names Beam's removal and the API level.

## Added 2026-10-14 — pushing a card to another person

From the sender's-playbook research ([`tap-to-share.md`](tap-to-share.md) § Pushing a card to another person).

- Unverified: **#30 (P2)** — what makes a pass **"eligible"** for Apple's hold-two-iPhones-together share (iOS 17.2+). Apple never defines it ("boarding passes, movie tickets, and other eligible passes", iOS 17.2 notes). A generic business-card pass did not trigger it on one owner test (2026-10-05) while Wallet Share + AirDrop worked; Apple's AirDrop guide starts proximity transfers only "if you're within close range of someone in your contacts", so that test does not separate pass eligibility from a contacts gate. How to verify: on the same two phones run (H0) a known-eligible pass first, then (H1) mutual contacts, (H2) two different Apple Accounts, (H3) *Bringing Devices Together* on + both unlocked, (H4) one payload signed as `eventTicket` / `generic` / `storeCard`. **Narrowed 2026-10-14:** no `pass.json` key, entitlement or vendor setting gates it (full key reference checked — `sharingProhibited` is the only sharing key), so the issuer has nothing to turn on; Apple Staff says app proximity shares need "known" contacts (forum 738469); one hands-on report has strangers do NameDrop first, then a second touch hands over the pass (Tom's Guide, a rail ticket). Ranked suspects for a generic pass that shows **no glow at all**: phones not mutual contacts / same Apple Account → phone settings or iOS < 17.2 → receiver already holds the pass via iCloud → procedure → pass style. Full protocol: [`tap-to-share.md`](tap-to-share.md) § Hold-to-share, in detail.
- Unverified: **#31 (P2)** — a **recipient-less `sms:` link with a prefilled body**. RFC 5724 has no recipient-less form; Apple's archived SMS-links reference says "The URL string must not include any message text." Hands-on evidence: iPhone `sms:&body=…`, Android `sms:?body=…` (MEAS). The often-quoted cross-platform `sms:?&body=…` has no current test. How to verify: open each form on current iOS and Android and record whether the body arrives.
- Unverified: **#32 (P2)** — the **`x-safari-https://`** scheme that opens a URL in Safari from an in-app browser. Undocumented by Apple. MEAS: works on iOS 15/17/18, "On iOS 16, this apparently does not work" (Tietze, 2024); "unreliable" inside Instagram, where Meta's own `instagram://extbrowser/` works (plugwith.me device tests, 2026). Never make it the only route — always print the by-hand step beside it. How to verify: tap it from Instagram, Facebook, LinkedIn and TikTok on the current iOS.
- Unverified: **#33 (P2)** — whether Google Wallet's holder-side **Share** ("You can share a pass if it has Share above it", DOC support.google.com/wallet/answer/12060038) appears on **Generic** passes, and which issuer setting controls it. PassKit (2024) says Google has no built-in sharing; Google's page says some passes do. How to verify: save a Generic pass on a current Android device and look for Share above it.
- Unverified: **#34 (P3)** — Google's behaviour when `multipleDevicesAndHoldersAllowedStatus` is **unset** on a class. Not documented. A card issued as one object saved by many people must set `MULTIPLE_HOLDERS` explicitly (`ONE_USER_ALL_DEVICES`: "Once the first user saves the object, no other user will be allowed to view or save it"). Also undocumented: whether a Save JWT that names an **existing** class updates it — PATCH the class instead.
- Unverified: **#35 (P3)** — whether a `MULTIPLE_HOLDERS` object update reaches **every** holder. Follows from there being one object; class updates are DOC'd to propagate "across all Passes Object instances"; no page states it for an object.
- Unverified: **#36 (P3)** — whether the hold-together pass share is exempt from iOS 26.2's **AirDrop code** requirement for non-contacts ("if someone tries to send you an item with AirDrop and they're not in your contacts, they must use an AirDrop code"). Not found.
- Unverified: **#37 (P3)** — what the iOS share sheet does with `navigator.share({ files: [<.pkpass File>] })`. Safari's `canShare` has no MIME allow-list (DOC, WebKit `Navigator.cpp`); Chrome's permitted list has no `.pkpass` or `.vcf` (DOC, Chromium FILE_TYPES). Share the URL instead until tested.

## Added 2026-10-18 — straight to Wallet from the QR and the tag

From [`tap-to-share.md`](tap-to-share.md) § Straight to Wallet from the QR and the tag.

- Partly resolved 2026-10-18: **#38 (P2)** — whether iOS Safari presents the **Add-to-Wallet sheet for a script-initiated navigation** to a `.pkpass` with **no user activation**. **Now evidenced:** MEAS (owner device test on a real iPhone, 2026-10-18): a card URL ending `#add-to-wallet`, opened directly in Safari on RavenPower's preview (`preview.ravenpower-sites.pages.dev/connect`) and on production (`www.ravenpower.net/connect`), showed Wallet's pass sheet (Add / review) with **no tap**. So iOS Safari does present the sheet for a script-initiated `location.assign()` to a `.pkpass` made about 150 ms after page load without user activation. **Still open:** the iOS version (not recorded); the Camera QR banner and NFC-tag notification entry points themselves (the test opened the URL directly in Safari); and a non-Safari default browser. Where it does not appear, the person simply lands on the card (the page they would have seen anyway). How to verify the rest: on a current iPhone, record the iOS version, open the same marked URL from the Camera and from an NFC tag, then repeat with a non-Safari default browser. Control: the same URL without the fragment shows only the page.

## Cross-platform asymmetries worth a second look

- **Headshots.** Google states flatly that "personal images" are **not supported** on passes (documented, not a VERIFY item). Apple has no equivalent statement in the docs reviewed (#29). If RavenPass wants a photo on the card, the design may differ per platform — or the photo lives only behind the URL.
- **Front-of-pass tappable link.** Google has `appLinkData` (allowlist-gated, #8). Apple has nothing equivalent before iOS 27 Featured Actions (#11), and `appLaunchURL` only launches an associated App Store app. #8 and #11 together decide whether "tap the pass → lead form" is achievable at all without a native app.
- **Doc freshness.** Google Wallet pages said "Last updated 2026-10-08"; Android pages "2026-10-01." Apple's Wallet guides describe iOS 27 features, but the `Pass` reference lags the guides (#3). Re-run this sweep after the next Apple release.
