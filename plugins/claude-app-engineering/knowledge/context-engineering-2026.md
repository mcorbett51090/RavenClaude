## The shift: from prompt engineering to context engineering
With **1M-token** context (every current model — Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5 — and legacy Opus 4.6+/Sonnet 4.6+; 1M is the default, no beta header; verified 2026-10-13), the question is no longer "how do I word the prompt" but **"what is the right *set of tokens* in the window at this step, and in what order."** More context is not better — every token competes for attention; irrelevant or stale context degrades quality ("context rot"). Curate deliberately.

## The levers
1. **Caching layout** — stable, high-value context above the breakpoint (system, tools, long static docs); volatile below. The cheapest way to *keep* large context is to cache it (0.1× read on most models; 0.05× on Opus 5.5 and Sonnet 5.5, 0.025× on Fable 5.1/Mythos 5.1 — verified 2026-10-13 against the models overview). See [`prompt-caching-playbook.md`](prompt-caching-playbook.md).
2. **Retrieve vs hold** — under ~200K tokens (~500 pages, per Anthropic's contextual-retrieval post, re-read 2026-10-13) + static → just hold the corpus in context; large/dynamic → retrieve the relevant slice (RAG). The boundary is the first context-engineering decision ([`retrieval-and-rag-2026.md`](retrieval-and-rag-2026.md)).
3. **Order matters** — put long reference material **first** (cacheable + better recall), the actual task/question **last** (Anthropic: queries at the end can improve quality by up to 30% on complex multi-document inputs; verified 2026-10-13); ask Claude to quote the relevant span before answering long docs.
4. **Context editing / compaction** — for long-running agent sessions, prune or summarize stale turns/tool-results so the window holds *current* signal, not history. The Agent SDK manages this; in raw Messages-API loops you own it (summarize old turns, drop superseded tool results — but mind cache invalidation).
5. **The memory tool** (**GA on the Messages API — no beta header**; verified 2026-08-06, re-verified 2026-10-13 — SDK helpers still live in the beta namespace — against the [memory-tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)) — persist durable facts/state *outside* the window and recall on demand, instead of carrying everything inline. It is **client-side**: Claude only *requests* the file operations and your app executes them, so the redaction pass (no secrets/PII), the eviction policy **and** the path-traversal defence are all yours ([`server-side-tools-and-files.md`](server-side-tools-and-files.md); the five distinct memory surfaces are mapped in [memory surfaces (2026)](../../memory-engineering/knowledge/memory-surfaces-2026.md)).
6. **Sub-agent context isolation** — give each sub-agent a *focused* slice, not the whole history (orchestrator-worker — [`agent-orchestration-patterns.md`](agent-orchestration-patterns.md)). Fresh, scoped context produces better per-task output and controls cost.

## Thinking config (dated — keep in the capability map)
- **Adaptive thinking** is the mode on every current model (steered by `effort`). Manual extended thinking (`type: "enabled"` + `budget_tokens`) is deprecated on Opus 4.6/Sonnet 4.6 and **not accepted on later models** (verified 2026-10-13).
- **Sampling params:** on Opus 4.7+, Sonnet 5+, Haiku 5.5, Fable/Mythos, any non-default `temperature`/`top_p`/`top_k` is a 400 on every request, thinking or not; on older models the restriction applies only while thinking is on (verified 2026-10-13). The old "temperature unset/1" note was the older-model rule.
- **Thinking blocks consume context + are cached** alongside content (prior-turn blocks kept by default on Opus 4.5+, Sonnet 4.6+, Haiku 5.5, Fable/Mythos; verified 2026-10-13). Keep the thinking config **and the top-level effort level** stable across turns: changing either invalidates cache breakpoints. Verify exact params in [`model-selection-and-2026-capability-map.md`](model-selection-and-2026-capability-map.md).

## Anti-patterns
- Dumping the whole conversation/corpus "just in case" — pay for tokens that dilute attention.
- Letting an agent's window fill with stale tool-results across a long session (no compaction) → quality + cost decay.
- Re-ordering or mutating cached context per request (busts the cache).
- Using RAG when the corpus fits in context (needless complexity), or stuffing a huge dynamic corpus into context when retrieval is the right move.
